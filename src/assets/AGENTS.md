# Rules for `src/assets/`

- After a remix, every pointer under `src/assets/` is re-uploaded into this project's storage (`lovable-assets create`) and every URL reference rewritten; a pointer carries the previous project's id, so images load in the sandbox but break once published. A pointer with no copy in the repo must have its bytes fetched over HTTP from a host that still serves them — the running dev server proxies `/__l5e/assets-v1/<asset-id>/<filename>` — because `lovable-assets get` refuses any pointer or `r2_key` outside the current project. `src/data/media-archive.json` and the `media_archive` record keep filenames, checksums and source download URLs; why: migration must copy original files as well as code, and public Cloud Storage is blocked by workspace policy.
- Every media pointer under `src/assets/` also has its real file next to it, code imports the real file, and database image paths point to `public/` files; why: `/__l5e` asset URLs only work on Lovable hosting, so photos must survive deploys elsewhere (e.g. Vercel). The one exception is a pointer whose bytes exceed the repo's 10 MB tracked-file limit (`nempo-feed-slide-32.mp4`): it stays pointer-only, because a tracked copy would fail the repository-completeness guard.
